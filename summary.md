# RAGC Simulator: Internal Documentation & Presentation Guide

This guide breaks down each visualization generated by the RAGC (Register Allocation with Graph Coloring) simulator. It highlights the advantages of the **Pressure-Ranked Chaitin** approach over the **Classic Chaitin** approach.

---

## 1. Register Pressure Heat Map & Live Range Gantt Charts

### A. Register Pressure Heat Map

**What it shows:**
This side-by-side heat map displays the exact "register pressure" at every single instruction in the program.

- **X-Axis:** Instruction index (the line of code executing).
- **Y-Axis:** Variable names.
- **Color Intensity:** Represents the "pressure." Higher intensity (darker/warmer colors) means that many variables are simultaneously _live_ (needed in a register) at that specific instruction. Additionally, variables inside loops receive an artificial intensity boost to reflect their heavier execution frequency.
- **Red "X" Markers:** Indicate variables that had to be spilled (saved to memory) because the pressure exceeded the available physical registers `k`.

> "Here we can visualize where the register pressure peaks in our program. The classic allocator often spills simply because pressure is high, without looking at the cost. By comparing both modes, you'll notice exactly which variables each algorithm chose to spill (marked with the red X). Notice how the Ranked algorithm aims to keep those high-intensity (loop-heavy) areas clear of spills, shifting the burden to less critical variables where possible."

### B. Live Range Gantt Charts

**What it shows:**
A timeline for every variable showing precisely when it starts being live and when it dies.

- **Bar length:** Spans from the variable's first definition to its last use.
- **Opacity:** Indicates the loop depth of the variable. Variables declared inside deep nested loops appear more opaque (solid).
- **Color:** Represents the physical register assigned (e.g., R1, R2). Spilled variables are distinctly colored **Red**.

> "The Gantt chart maps the lifetime of every variable. The overlapping bars represent interference. Using the opacity, we can instantly tell which variables are inside loops and therefore more expensive to spill. Looking at the assigned colors helps us verify that no two overlapping variables ever get exactly the same physical register color—unless they are spilled."

## 2. Comparison Charts: Count & Cost

### Spill Count & Cost Comparison (Grouped Bar Chart)

**What it shows:**
Direct quantitative comparison between the Classic and Ranked allocators.

- **Spill Count:** Total number of variables that were ousted to memory.
- **Spill Cost (weighted):** The algorithmic penalty for spilling. Spilling a variable inside a loop costs exponentially more than spilling a short-lived linear variable.
- **Delta Annotations:** The numbers hovering above the bars show the percentage improvement or degradation of the Ranked algorithm versus the Classic algorithm.

> "This is our bottom-line metrics chart. While the total _number_ of spills might sometimes be similar, the true measure of a good allocator is the _Spill Cost_. Because the Ranked approach factors in loop depth and def-use distance, it consistently achieves lower overall spill costs for demanding programs, resulting in more efficient compiled machine code."

## 3. Composite Score Breakdown

### Score Scatter Plot (Ranked Mode Only)

**What it shows:**
This plot is the "brain" of the novel Pressure-Ranked algorithm.

- **Equation used:** `Score(n) = w₁ / (def_use_distance × (depth+1) × (degree+1) × w₂)`
- **X-axis:** The order in which nodes (variables) were processed during the _Simplify_ graph reduction phase.
- **Y-axis:** The computed composite score.
- **Logic:**
  - _High Score:_ The variable is cheap to spill (short-lived, outside loops, low pressure). These are simplified (removed from the graph) _first_.
  - _Low Score:_ The variable is expensive to spill (long-lived, inside heavy loops). These are kept in the graph the longest so they are colored first and are more likely to get a physical register.
- **Diamond Markers:** Indicate moments when the algorithm was stuck (no nodes had fewer than `k` neighbors) and had to mark a node as a _potential spill_.

> "This graph explains _why_ the Ranked allocator performs better. We assign a mathematical score to each variable. Variables with high scores are cheap to spill, so they are processed earliest. The graph shows the decreasing curve of scores—proving that our algorithm effectively protects high-priority loop variables by processing them last."

## 4. Interference Graph & Step-by-Step State

### Initial & Final Assignments (Node-Edge Networks)

**What it shows:**
Standard Graph Coloring visualizations.

- **Initial Graph:** The raw interference graph where edges connect variables whose live ranges overlap. To compile without spills, this graph must be colored with `k` colors so no adjacent nodes share a color.
- **Final Assignment (Classic vs Ranked):** The resulting colored graphs. Spilled nodes are visually separated (usually rendered as red diamonds or distinct disconnected nodes).
- **Graph Stepper UI:** The timeline slider allows you to step through the entire _Simplify -> Potential Spill -> Color -> Actual Spill_ stack process instruction-by-instruction.

> "Register allocation is fundamentally a graph coloring problem. On the left is the raw interference graph of our program. On the right, you can see how both algorithms resolved the coloring using exactly `k` colors. I can also use the step-by-step slider below to show you exactly the order in which nodes were pushed onto the stack and popped off for coloring, highlighting the exact moment a spill was forced."

### Tips for Answering Questions during Presentation:

- **Why does loop depth matter so much?** In real execution, a variable spilled inside a loop might be read/written 10,000 times, causing massive CPU delays. A variable outside a loop is only saved/loaded once.
- **What if Ranked and Classic have the same spill cost?** For very simple programs, "dumb" coloring works just fine. The Ranked heuristic shines on complex code with high register pressure (when max concurrent live variables `> k`).
